# T6.4 — Project lifecycle observations and verified delivery evidence

## Purpose

Map APRL's persisted task lifecycle into the frozen v1 observation without confusing coding completion, review approval, and verified landing. Persist and replay trusted evidence; worker-submitted JSON is never proof of delivery.

## Dependencies

Begin after T6.2.R and T6.3.R have independently approved and verified their exact landings.

## Ownership

Own only the narrow `internal/plantasks` projection/evidence implementation and focused state/store integration tests named in the accepted T6.0 mapping. Do not change generic task tooling, the wire contract, HTTP routes, the scheduler, or production registration.

## Requirements

- Use the single APRL lifecycle/scheduler and its canonical task IDs. Map each wire child to its APRL `T-<UUID>` claim row consistently; external caller IDs stay opaque. Map `re_review` to APRL's rereview stage. Do not create a second scheduler or duplicate the stable initial review/delivery-gate child; follow the T6.0 crosswalk for its stable UUID and delivery projection.
- Keep coding handoff, review verdict, bounded corrections, re-review, merge, and verified landing distinct. A handoff or `changes_requested` result is not delivery success. Ordinary descendants become releasable only after actual verified landing. Advisory readiness is not authorization; admission remains an atomic, current-revision, current-claim decision.
- Add an additive, strongly typed host-returned `LandedEvidence` path containing every frozen landed-evidence field: repository/target/PR, reviewed source head and base, policy revision, landed commit, source digest, independent reviewer, author, verifier identity, and verification time. The current `OutcomeVerifier.Verify(...) error` result alone is not proof and must not be treated as returning this evidence. Validate the typed evidence against the current task, PR tuple, review/merge lineage, and snapshot, then persist the evidence atomically with the state transition before projecting `landed`. Worker-submitted receipts never populate or replace this host proof. Never synthesize proof from a label, checkbox, PR URL, merge commit alone, or a nil error.
- Persist a positive external observation sequence and exact replay. Same-sequence identical requests return the same stored observation; conflicting, stale, skipped, or out-of-order updates cannot overwrite newer facts. `State.Revision` is not a substitute for external sequence.
- Cancellation and expiry fence new admissions before any external fact update. Late trusted facts may be retained for reconciliation but cannot reopen descendants or erase prior evidence. Paused, cancelled, stale, unavailable, or ambiguous states remain non-releasable.
- Keep v1 subscription-only accounting within the qualified host policy. Do not claim monetary settlement or fabricate a settlement ID. Preserve `unknown`/non-settled exposure when execution or usage is ambiguous; never round it to known zero because work ended or landed.

## Verification

Use persisted-state integration tests for each observation and receipt transition, replay, stale sequence, cancellation/expiry race, and review independence. Assert the exact projected state, task IDs, readiness/admission result, and receipt bytes after store reopen. Include genuine-red tests for missing or mismatched source head/base, same author/reviewer, forged verifier evidence, receipt mutation, and stale observation rollback; restore each predicate and rerun. Record actual positive test counts with zero skips/failures.

## Delivery

Commit only the accepted T6.0 projection/evidence paths and focused tests. Hand off the exact PR URL/head/base for independent T6.4.R review. T6.5 waits for this task and review to land.

## Boundaries

This task proves projection and receipt validation using the trusted test verifier and durable store. It does not establish a production verifier, broker, GitHub credential authority, live provider, or runtime activation.

## Implementation decisions

The typed verifier receives the complete canonical State so it can bind the revision and every author in the correction lineage. External fetching occurs before database locks; bounded local verification occurs under the transition lock. Only a private verified transition can introduce host proof. Public store callbacks, ordinary worker receipts and initial state cannot introduce it. Existing unbound error-only verifier behavior remains compatible but cannot establish caller-facing v1 delivery.

The source digest is lowercase SHA256 of the raw binary Git root-tree object body obtained with `git cat-file tree <reviewed_head>^{tree}`, without the Git object header or text conversion. The verifier must prove the actual landed tree equals the reviewed tree under the exact reviewed-base merge policy. Base drift requires re-review. This digest is distinct from a request digest, plan digest or native Git object identifier.

Projection uses persisted transition time and canonical task IDs, including all fix and re-review tasks. An unchanged external sequence returns byte-identical observations; elapsed wall-clock time alone does not rewrite those bytes. Current admission separately enforces the exact delegated deadline.

Host-authenticated late landing facts retain the complete proof in a bounded separate audit map. They never complete tasks, release claims or descendants, change cancellation, or establish a landed observation. Exact replay requires the original revision, actor, input and full proof, with fresh authentication and verification; it performs no write or sequence increment.
