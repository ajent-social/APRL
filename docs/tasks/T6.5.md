# T6.5 — Prove the composed v1 lifecycle through the ordinary generic task flow

## Purpose

Exercise the assembled codec, durable ledger, HTTPS handler, lifecycle projection, and the already-published generic task shim as one bounded fixture. Prove that APRL remains the sole lifecycle scheduler and that ordinary generic apply/claim operations use the service's current authoritative admission.

## Dependencies

Begin only after T6.1.R, T6.2.R, T6.3.R, and T6.4.R have independently approved and verified their exact landings.

## Ownership

The scenario lane owns `tests/system/code_delivery_v1_test.go`, the bridge lane owns `tests/system/code_delivery_v1_shim_test.go`, and the coordinator owns `tests/system/code_delivery_v1_shared_test.go`. Helpers remain self-contained in these explicitly tagged files. A minimal existing provider-boundary correction is permitted only after the actual published shim reproduces the incompatibility, with a named regression and independent review. Use real PostgreSQL, loopback HTTP, and explicit test-only host authentication/verifier adapters. Do not change generic shared tooling, package registries, installed profiles, runtime factories, the plan, or production configuration.

## Requirements

- Exercise the actual published generic task shim in its normal snapshot → claim/WON → fresh snapshot → atomic admit → bounded execute/result → fenced acknowledgement flow. Use a temporary test registry/transport and canonical APRL claim IDs; do not edit or install a user/global registry or profile. `ready` and a checked `done` box remain advisory and cannot bypass server admission.
- Submit a frozen canonical v1 request through the loopback handler backed by real PostgreSQL. Cover a lost PUT response recovered by caller-scoped GET, concurrent identical PUT yielding one lifecycle, changed-digest conflict, wrong caller, and durable identical observation replay after service/store reconstruction.
- Exercise both the existing standalone path and delegated v1 path through the same APRL adapter/scheduler. For each, run ordinary author → independent review → `changes_requested` → bounded fix/re-review → exact reviewed head/base → trusted merge/landing evidence. Demonstrate that the binding addition leaves standalone consumers intact, negative review never becomes success, the stable gate has one claim identity, and only exact verified landing releases ordinary descendants.
- Race an old claim/revision and a late result against a newer lifecycle revision, expiry, and cancellation. Denials must leave ownership, budget, durable task status, observation sequence, and receipt unchanged; uncertain outcomes remain unknown and held.
- Assert v1 subscription-only policy, global attempt accounting including mandatory review, exact expiry fencing, zero monetary values only where host policy proves subscription-only/no exposure, and no fabricated settlement ID. Unknown exposure remains non-settled.
- All test authenticators, grant checks, host verifiers, and any process/runtime doubles are explicit fixtures. A fixture can prove only its injected boundary; it never registers, activates, or qualifies a production provider/profile/factory.

## Verification

Run the focused `tests/system` selector and report actual terminal test counts, failures, and skips. The fixture must use real owned PostgreSQL and loopback HTTP, with no silent skip when services are missing. Include genuine-red/restored checks for authorization, stale revision, exact head/base receipt, independent reviewer, cancellation/expiry fencing, and generic-shim admission bypass. Verify restart/replay from persisted PostgreSQL state. Keep the test resource finite and uniquely named, and clean only resources created by this fixture.
